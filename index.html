01

Get started in 5 steps

  1. Create or select a project.

    Use the project selector to work in the right project. Keep work for one product or team together.

  2. Create a User Story.

    Open User Stories and add a short, user-focused outcome. If creating a story through a task, enter the same story title on each linked task.

  3. Break the story into tasks.

    Make tasks small enough to estimate, assign, and finish. Add a clear description, owner, priority, and dates when useful.

  4. Plan delivery.

    Set the Program Increment (PI), Sprint, Feature, and story points consistently with your team's planning approach.

  5. Update work honestly.

    Move tasks from To Do to In Progress to Done as work changes. Review insights regularly and adjust the plan when reality differs.

02

Understand the work hierarchy

Arcflow provides fields to organize work. Teams may use different Agile frameworks, so agree on definitions and use them consistently.

Portfolio / ProjectThe product, initiative, or shared workspace being planned.
↓
Program Increment (PI)A larger planning horizon used by some teams to align multiple sprints.
↓
FeatureA meaningful capability or slice of product functionality.
↓
User StoryA user-centered outcome or need, with acceptance conditions.
↓
TaskA concrete piece of work required to deliver the story.
↓
SubtaskA smaller step within a task, where further breakdown helps.
Important: These fields do not automatically enforce a strict parent-child hierarchy. PI, Sprint, Feature, and User Story are task fields; a task can be associated with them by setting those values consistently. Dependencies are separate links that describe ordering or blockers.
03

Glossary: the words you'll see

Project

A workspace for a team's related tasks, stories, and planning.

Program Increment (PI)

A longer planning period that may contain multiple sprints. Use your organization's agreed PI names.

Sprint

A fixed timebox, often one to four weeks, in which a team plans and completes work.

Feature

A product capability that may be delivered through several user stories.

User Story

A concise description of value from a user's perspective. Example: “As a customer, I want to track my order so I know when it will arrive.”

Acceptance criteria

Specific conditions that must be true for the story to be accepted. Write them so another person can verify them.

Task

A unit of work that someone can own and move through the board.

Subtask

A smaller action inside a task. Use it for clarity, not to fragment every tiny action.

Dependency

A relationship where one task relies on another. A blocked task may not progress until its dependency is resolved.

WIP limit

Work-in-progress limit: a cap on items in a status column, used to expose overload and encourage finishing.

Backlog

Work considered for future delivery but not necessarily committed to a sprint.

Spillover

Work planned for one sprint that remains incomplete at the sprint's end.

04

Statuses and the right workflow

To Do

Work is understood enough to be queued but has not started.

→
In Progress

Someone is actively working on it. Keep WIP realistic.

→
Done

The agreed completion conditions are met and the work is verified.

Update status when the work actually changes, not just to make a chart look better. If review or testing is a distinct stage, define how your team represents it (for example, task description/checklist or story lifecycle).

User Story lifecycle

Draft → Ready → In Progress → In Review → Accepted. Draft means the story is still being shaped; Ready means the team believes it can start; In Progress means implementation has started; In Review means it is awaiting validation; Accepted means the story has been reviewed and meets its acceptance criteria. This lifecycle is distinct from the To Do / In Progress / Done status on individual tasks.

05

What are story points?

Story points are a relative estimate of effort and uncertainty for a story or piece of work. They are not hours, days, money, or a measure of an individual's productivity.

1 point

Very small and well understood compared with the team's baseline.

2–3 points

Small, limited complexity, few unknowns.

5 points

Moderate work with several steps or some uncertainty.

8+ points

Large or uncertain. Consider splitting it into smaller deliverable stories.

These are examples, not universal rules. Each team calibrates estimates using shared reference stories. Many teams use a Fibonacci-like scale (1, 2, 3, 5, 8, 13). Estimate complexity, effort, and uncertainty together; do not compare points between teams.

How Arcflow uses points

The task editor stores points on each task. Story cards can show the sum of points across linked tasks; Agile Insights uses committed and completed points for its sprint metrics. Avoid assigning the full story estimate to every task, or the totals will be inflated. Choose one consistent policy: estimate stories and report story-level points, or estimate tasks and sum them—do not mix the two.

06

How to track work well

  • Write outcomes, not vague titles. Prefer “Allow a customer to reset a password” over “Password work.”
  • Define acceptance criteria. State how the team will know the story is complete.
  • Keep tasks actionable. Each task should have one clear outcome and an owner where possible.
  • Use consistent labels. Pick one naming convention for PI, sprint, and feature; avoid variants such as “Sprint 1”, “S1”, and “sprint-01” for the same sprint.
  • Estimate before committing. Include testing, review, integration, and other necessary work in the plan.
  • Limit work in progress. Finish or unblock existing work before starting too many new tasks.
  • Review dependencies and dates. Set realistic start/end dates and call out blocked work early.
  • Close only verified work. Done means the team's definition of done is satisfied, not merely that coding stopped.
  • Use charts to learn. Investigate missed forecasts and bottlenecks; do not use velocity to rank people.
07

Read Agile Insights and graphs

Completion rate / progress bar

Shows the share of tasks marked Done out of the tasks included in the view. A high percentage is only meaningful if statuses are current and the scope is clear.

Committed Points

The points planned or committed for the selected sprint, based on the app's sprint data and fields. Treat it as the planned workload, not a promise of guaranteed delivery.

Completed Points

Points attached to work recorded as completed. Compare with committed points to understand how much planned work was finished.

Velocity Chart

Compares committed and completed points across sprints. Use several sprints to understand a team's own delivery pattern; one sprint is noisy. Velocity is for forecasting, not individual performance evaluation.

Burndown Chart

Shows remaining work over time against a reference/ideal trend. If actual remaining work stays above the ideal line, work may be progressing more slowly than planned or scope may have increased. A flat line can mean no work has been completed or data has not been updated.

Spillover Tasks

Work that remains incomplete after the sprint it was planned for. Repeated spillover can point to over-commitment, hidden dependencies, interruptions, or work that is too large.

Overdue Open

Open tasks whose end/due date has passed. Review date accuracy, blockers, priority, and whether the plan needs to change.

Sprint Calendar

A calendar view to see work dates and sprint timing. It depends on task dates and consistent sprint labels.

Read trends, not isolated numbers. Check that sprint names, points, dates, and task statuses are maintained consistently before drawing conclusions. If a chart looks wrong, first inspect the underlying task records and selected filters.
08

Filters, sorting, and board controls

Search

Find tasks by task name, story, assignee, feature, or other indexed/displayed text.

PI / Sprint / Feature / Assignee filters

Narrow the displayed work to a planning period, capability, or owner. Remember that metrics may reflect the currently selected scope.

Sort cards

Change the order in which tasks appear; sorting does not change their status or priority.

WIP limits

Set a maximum for a column to highlight overload. A limit is a conversation starter; it does not replace team coordination.

List View

A table for scanning, sorting, selecting, and bulk-updating tasks.

Kanban View

A visual board grouped by task status. Move work through the flow as it progresses.

User Stories

Review stories, their linked tasks, lifecycle, and aggregate points.

Agile Insights

Review sprint calendar and delivery metrics to support planning and retrospectives.

09

Worked example: from idea to delivery

Feature: Account security

User Story: As a user, I want to reset my password so I can regain access securely.

Acceptance criteria: A valid reset request sends a time-limited link; invalid/expired links are rejected; success confirms the password was changed.

Tasks: Build reset-request screen (3 points); implement reset-token validation (5 points); add tests and review (2 points).

Total task-estimated points: 10, if your team uses task-level estimates consistently.

Sprint: Sprint 04. PI: PI 2026-Q4. Owner: assigned team member. Status: tasks move To Do → In Progress → Done; story moves through its own lifecycle to Accepted after verification.
